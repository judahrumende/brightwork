### Replay and staging

The read-only logged-out HAR replay against the local built server matched all seven captured requests. This includes the fixed Brightwork landing variant at `GET /api/landing-test` and the public catalogue at `GET /api/billing/plans`. The catalogue shows starter credits and lists the configured subscription only when Stripe returns an active fixed recurring test price. The replay used the unconfigured catalogue. A separate provider fixture verified the configured offer, including currency, price, billing interval and renewal credits.

The read-only signed-in replay uses an isolated Postgres schema, a synthetic session and a mapping from the captured workspace to a new Brightwork workspace. The initial run matched 27 requests and reported 906 mismatches across 97 method and path pairs. Run directions, questions and tasks brought the match count to 218. With Run session and conditional history reads, replay matched 340 requests and reported 593 mismatches across 94 pairs. Adding Inbox revisions and drafts, social post drafts, and websites awaiting approval brought replay to 444 matches and 489 mismatches across 90 pairs. Build activity and conditional reads brought replay to 533 matches and 400 mismatches across 90 pairs. Scoped chat history and queue reads brought replay to 573 matches and 360 mismatches across 90 pairs. The conversation list and title reads increased matches to 577 and reduced mismatches to 356 across 88 pairs. It skipped 52 records in each run. The fixture maps the most frequently requested Run history to a persisted synthetic Run. It also maps the most frequently requested creation to a saved Brightwork website. Other history and artifact IDs are still unmapped. Creation and version responses now read persisted drafts, published revisions and restore lineage. The capture still expects metadata that Brightwork does not yet store, including thumbnail and Build change identifiers. The Build activity fixture also maps a captured Build ID to its saved result. The workspace now returns active builds, approvals and version provenance. Detailed Build timing, validation, image and planning reports still differ from the capture. Website change reads now compare the exact pending draft against the stored published snapshot. Their captured handoff and image annotations remain open, so the aggregate match count is unchanged. Chat and queue reads use native turn records and omit legacy fields Brightwork does not persist, including separate message IDs and prediction usage metadata. Expanded Run responses use native turn data and still differ from the capture's turn timing, message IDs and usage fields. Replay uses local ETags and sends no captured credentials.

To reproduce locally, run `pnpm --filter @brightwork/api exec tsx --env-file="$PWD/.env" test/replay-signed-in.ts` from the repository root with local Postgres and Redis running. The harness removes its isolated schema at exit. The report groups identical errors by method and path.
